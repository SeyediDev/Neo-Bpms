# ممیزی مسیر مستند/فایل در فرم‌ساز — ۲۰۲۶-۰۹-۲۷

**نتیجه: مسیر فعلی برای تأیید عملیاتی آماده نیست.** از ۳۱ سناریوی اجرایی، ۱۰
مورد موفق و ۲۱ مورد ناموفق‌اند: سرور ۶/۲۴، JavaScript برابر ۴/۷. این اعداد
مربوط به ممیزی فایل‌اند، نه آزمون‌های قبلی تم و فیلتر. شکست‌ها عمداً با exit code
غیرصفر گزارش می‌شوند؛ انتظار آزمون برای تطبیق با باگ ضعیف نشده است.
در این مرحله کد محصول اصلاح نشده؛ گزارش، هارنس قابل‌تکرار و راهنمای همراه اصلاح شده‌اند.

[نتایج ساختاریافته و شناسهٔ سورس‌های آزموده‌شده](audits/document-flow-2026-09-27.json)

## مسیر واقعی اجرا

1. مدل `TVariableTypes.File` به کنترل `File` نگاشت می‌شود؛ `AdvancedUpload`
   کنترل جداگانه‌ای است. `Multiple`، `UseFileServer`، `DocumentType` و
   `ShowDocumentInPage` در متادیتا وجود دارند، ولی وجود گزینه تضمین اجرای مسیر نیست.
2. `FileHtmlControl` و `FormFileManager` فایل عادی را به شکل
   `data:<mime>;base64,<content>|<filename>` در hidden input می‌گذارند و Action را
   `Upload` می‌کنند. ارسال فایل ناموفق/درحال آپلود در FineUploader متوقف می‌شود.
3. `AdvancedUpload` با FineUploader به `Upload/Upload?isConcurrent=True` قطعه
   می‌فرستد و با `Upload/Success` تکمیل می‌کند؛ خروجی فرم UUID و Action=`Move` است.
4. `ApplyFormDocuments` اعمال Upload/Move/Remove را به `ICmmnDocument` می‌سپارد
   و شناسهٔ برگشتی را روی رکورد می‌نویسد. این لایه صرفاً رابط است؛ ذخیرهٔ نهایی را
   پیاده‌سازی میزبان تعیین می‌کند.
5. در Hyper، `CmmnDocument` به `AddDocumentCommand` می‌رسد. پیش‌فرض محتوا به
   `IObjectStoreService` و MinIO می‌رود؛ `SaveContentInRecord` مسیر باینری DB است.
   شیء با کلید `doc-{Id}` و JSON حاوی `ObjectStoreDto` نگهداری می‌شود؛ فایل خام S3 نیست.
6. دانلود از `Download/DL?id=...`، آداپتور Hyper، `GetOneDocumentQuery` و سپس
   DB یا Object Storage می‌گذرد. نمایش داخل فرم از `DocumentView` استفاده می‌کند.

## یافته‌های تکمیلی سورس، خارج از شمار آزمون‌های اجرایی

- `RemoveDocumentCommandHandler` فقط Task.CompletedTask/Unit برمی‌گرداند؛ حذف
  سند انجام نمی‌دهد. با این حال ApplyFormDocuments مقدار فیلد را null می‌کند.
  `Upload/Delete` نیز NotImplementedException دارد و IObjectStoreService عملیات حذف ندارد.
- در مسیر دانلود بررسی صریح نسبت کاربر/رکورد/فیلد دیده نشد. تست منفی با دو حساب
  و دو سند لازم است؛ از تست مستقیم کلاس نمی‌توان دسترسی HTTP غیرمجاز را قطعی دانست.
- محدودیت پسوند فعلی در JavaScript است؛ allowlist سرور، quota، عمر staging، مالکیت
  آپلود، اندازه/تعداد قطعات، hash نهایی و سیاست هم‌زمانی/قفل باید تعریف شوند.
- JSON/Base64 و MemoryStream چند کپی کامل از فایل ایجاد می‌کنند. چانکی بودن انتقال
  مرورگر به معنی ذخیره‌سازی streaming یا multipart واقعی S3 نیست.
- تنظیم MinIO در Neo، SSL را صریحاً false می‌کند؛ cancellation در قرارداد ObjectStore
  وجود ندارد. ETag به‌تنهایی SHA-256 فایل اصلی نیست، خصوصاً برای multipart.
- نام اصلی فایل در AttachmentDto نادیده گرفته می‌شود. در HTML تصویر، MIME با پیشوند
  اضافهٔ image و UTF-8 خام ترکیب می‌شود. مسیر UseFileServer به GetPaintableFileInfo
  پیاده‌سازی‌نشده می‌رسد.
- تراکنش DB نمی‌تواند PUT شیء را rollback کند. تست خرابی پس از PUT و پیش از commit،
  پاک‌سازی شیء یتیم و جبران شکست هنوز لازم است. مسیر باینری DB نیز به آزمون SQL و
  بررسی محدودیت مدل Content نیاز دارد.

## تکرار آزمون

از ریشهٔ Neo-Bpms، با SDK .NET 10 و checkoutهای همسایهٔ Neo و Hyper:

```powershell
dotnet run --project tests/Neo.Bpms.DocumentFlow.Audit --disable-build-servers -p:UseSharedCompilation=false
node --test tests/Neo.Bpms.UI.MVC.Tests/Frontend/DocumentFlow.audit.test.cjs
```

مسیر همسایه‌ها قابل تغییر است: `-p:NeoRoot=<path> -p:HyperRoot=<path>`.
کد uploader/downloader، آداپتور Hyper، MIME detector و ObjectStoreService از فایل
اصلی لینک و کامپایل می‌شود. نوع Entity، sender، DTO درخواست‌ها و ControllerBase
مرزهای شبیه‌سازی‌شده‌اند؛ EF، authorization middleware و transaction واقعی در هارنس نیستند.
MinIO SDK واقعی با HttpMessageHandler حافظه‌ای آزموده شده؛ هیچ اتصال شبکه‌ای از آن
خارج نمی‌شود. JavaScript از منبع واقعی استخراج می‌شود و FileReader/jQuery شبیه‌سازی‌اند؛
این مجموعه آزمون مرورگر یا E2E نیست.

هارنس فقط فایل‌های کوچک در `TEMP/neo-document-audit/<random>` می‌نویسد؛ برای تست
حجم بزرگ، صرفاً عدد اعلامی بزرگ است. سند، رکورد، bucket یا فایل کاربر تغییر نکرد.

## پذیرش باقی‌مانده و ترتیب اصلاح

۱. قرارداد واحد بایت/نام/MIME و staging متعلق به کاربر؛ رفع شکست ذخیرهٔ عادی و Move.
۲. محدودسازی مسیر، اندازه، قطعات، کامل‌بودن، احراز هویت و مجوز سند؛ سپس retry/لغو/cleanup.
۳. دانلود null-safe، کش خصوصی، پیش‌نمایش، نام فایل و حذف هماهنگ.
۴. اتصال واقعی به bucket تست MinIO، آزمون SQL با دادهٔ disposable، خطای شبکه و
   جبران شکست تراکنش؛ سپس سناریوی کامل فرم‌ساز با دو حساب و چند نوع فایل.

محیط MinIO پیکربندی‌شده در Hyper loopback نیست. bucket آزمایشی مشخص نشده و
آزمون نوشتن روی سرویس واقعی انجام نشده است. نتیجهٔ فعلی تأیید تمام مسیر در محیط واقعی نیست.

Skill و recipe موجود `dynamic-form` در MCP به این ممیزی ارجاع داده‌اند؛ ابزار جدید
یا ادعای «آپلود امن» اضافه نشده و قرارداد پنج ابزار MCP تغییری نکرده است.

توضیح دسترس‌پذیری ضعف مسیر: بازتولید traversal روی کنترلر واقعی با پیاده‌سازی
موقت ICmmnDocument انجام شد. در Hyper فعلی، staging پیاده‌سازی‌نشده زودتر مانع
موفقیت همین مسیر می‌شود؛ این گزارش ادعای بهره‌برداری موفق علیه Hyper عملیاتی ندارد.
فعال‌کردن staging بدون اصلاح کنترلر، این مانع فعلی را برمی‌دارد.

اعتبارسنجی همراهان: ۱۹ تست Companion اجرا شد؛ ۱۸ موفق و یک مورد symlink به‌دلیل
محدودیت سیستم‌عامل skip شد. تست واقعی stdio برای recipe فرم و هر پنج ابزار موفق
بود. Skill نیز با quick_validate اعتبارسنجی شد. این موفقیت‌ها شکست‌های ممیزی فایل
را جبران نمی‌کنند.
